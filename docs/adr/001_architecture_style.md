# ADR-001: Модульный монолит вместо микросервисной архитектуры

## Контекст

Разрабатывается MVP информационной системы «AI Закупщик». Функциональный объём включает пользователей и организации, товары, складские остатки, продажи, поставщиков, рекомендации, закупки и CSV-импорт.

Команда проекта небольшая, основной приоритет MVP — быстро реализовать и проверить сквозной сценарий закупки. Требований к независимому масштабированию отдельных бизнес-доменов на этапе MVP нет. Прямые интеграции с 1С, МойСклад, Ozon и Wildberries также не входят в MVP.

Рассматривались два основных варианта:

1. микросервисная архитектура;
2. одно Spring Boot приложение с логическим разделением на функциональные модули.

## Решение

Для MVP выбрана **монолитная архитектура с логическим разделением Backend на функциональные модули**.

Backend реализуется как одно приложение Spring Boot и использует одну PostgreSQL базу данных.

Логические модули:
- Auth / Company;
- Product / Inventory / Sales;
- Supplier / Recommendation;
- Purchase / CSV Import.

## Последствия

### Положительные

- проще разработка и локальный запуск;
- проще интеграционное и сквозное тестирование;
- единая транзакционная модель и одна PostgreSQL база;
- проще развёртывание и DevOps;
- отсутствуют дополнительные сетевые взаимодействия между бизнес-модулями;
- архитектура подходит для MVP и допускает дальнейшее выделение сервисов при появлении реальной необходимости.

### Отрицательные

- все бизнес-модули разворачиваются совместно;
- отдельный модуль нельзя независимо масштабировать;
- ошибка внутри приложения потенциально влияет на весь Backend;
- по мере роста проекта потребуется дисциплина архитектурных границ.
